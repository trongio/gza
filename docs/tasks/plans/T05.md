## 1. Goal

Give `:core:predict` (pure Kotlin/JVM, no `android.*`, no `:core:ttc`) a deterministic
prediction engine that turns `:core:model` data (route schedules, live vehicle positions,
the stop, optionally the arrivals board) into the list of departures from one stop for
today and tomorrow, each with a scheduled time, a predicted time and a state. It picks the
right service period for each day (`serviceDates` first, weekday after the listed week),
handles times past midnight (`24:05` belongs to the previous service day) and never lists
arrivals at a pattern's last stop as departures. Its headline rule (PLAN.md 2.0): a bus
waiting between trips at the first stop of its pattern is `Waiting(leavesAt)` with
`leavesAt = max(its timetable departure, arrival + minimum turnaround)`, never "arriving
now", whatever the board says; a waiting bus whose time has passed becomes `Late` and its
time moves forward with each poll. The board and `arrivalDelay` are carried as hints only.
A small leave-by module turns a predicted departure plus walk minutes and a buffer into a
leave-by time and picks the best and fallback option for T07's hero card. Time comes from
an injected `java.time.Clock`, always evaluated in `Asia/Tbilisi`.

## 3. Design

### 3.3 Inputs (all `:core:model` types)

```kotlin
/** Everything the engine needs for one stop. The caller (T07 ViewModel) builds it from repositories. */
data class StopRequest(
    val stop: Stop,                          // id + location of the stop asked about
    val routes: List<RouteSnapshot>,         // routes serving the stop that the user wants
    val board: StopBoard? = null,            // hint only, never changes a time
    val memory: LayoverMemory = LayoverMemory.Empty, // returned by the previous predict() for this stop
)

data class RouteSnapshot(
    val route: Route,                        // id, shortName (joins the board), kind
    val schedules: List<RouteSchedule>,      // one per pattern the caller has; may be empty (missing)
    val patterns: List<Pattern> = emptyList(), // from RouteDetail, only for headsigns
    val positions: RoutePositions? = null,   // null = no live data (offline, error, not polled)
)
```

Decisions:
- **Stop location from `Stop`**, not from `PatternStops`: the stop asked about is the
  terminus whose layover matters, and `Stop` is always in Room. `PatternStops` are not
  needed in v1.
- **First and last stop from the schedule**: in a period, the `ScheduledStop` with the
  lowest `position` is the first stop, the highest is the last (TTC_API.md: positions match
  travel order). This works without `RouteDetail`, which can be missing or fail (route 469
  returned 500). `RouteDetail.patterns` is only used for headsigns.
- **Memory in, memory out**: the engine is a pure function
  `(request, clock) -> (departures, memory')`. The caller keeps `memory'` per stop (T07:
  a `MutableStateFlow<LayoverMemory>` per saved stop, not persisted) and passes it to the
  next call. This gives "arrival time" and "has not moved since its time passed" without
  the engine holding state.

### 3.4 Outputs

```kotlin
data class StopPrediction(
    val stopId: StopId,
    val now: ZonedDateTime,                  // the instant used, in Asia/Tbilisi
    val departures: List<PredictedDeparture>,// sorted, see below
    val missingTimetables: List<RouteId>,    // routes with no usable schedule for this stop
    val memory: LayoverMemory,               // feed into the next predict() for this stop
)

data class PredictedDeparture(
    val routeId: RouteId,
    val routeShortName: String,
    val kind: TransportKind,
    val pattern: PatternSuffix,
    val headsign: String?,
    val stopId: StopId,
    val serviceDate: LocalDate,              // the service day the time is listed under (24:05 keeps the earlier date)
    val scheduled: ZonedDateTime,            // timetable time, Asia/Tbilisi
    val predicted: ZonedDateTime,            // what the UI counts down to
    val state: DepartureState,
    val confidence: Confidence = Confidence.NotRated,
    val boardHint: BoardHint? = null,
)

sealed interface DepartureState {
    /** Parked between trips at this pattern's first stop; leaves at [leavesAt] (== predicted). */
    data class Waiting(val vehicleId: VehicleId, val leavesAt: ZonedDateTime) : DepartureState
    /** Was Waiting for this departure, its time passed and it is still parked. */
    data class Late(val vehicleId: VehicleId, val leavesAt: ZonedDateTime, val lateBy: Duration) : DepartureState
    /** First stop, live data fine, departure within 12 min and no bus there yet (prototype NOT_ARRIVED). */
    data object NoBusYet : DepartureState
    /** Timetable time only: downstream stop, later trips, or no live data. */
    data object TimetableOnly : DepartureState
}

/** Placeholder until T10 rates predictions (±1, ±4 min, timetable only). */
sealed interface Confidence { data object NotRated : Confidence }

/** The board row for this route (and pattern), as sent. Never used to compute a time. */
data class BoardHint(val realtimeMinutes: Int?, val scheduledMinutes: Int?, val observedAt: Instant)
```

- **No `Live` state in v1.** "Live" (a GPS ETA for a bus on its way, `stopsAway`) needs
  polyline projection, which is T10's scope; T10 adds `Live` to the sealed interface and the
  compiler then forces every `when` in T07 to handle it. v1 never claims a mid-route ETA.
- **Sorting**: by `predicted`, then `scheduled`, then route short name numerically (compare
  length, then string: every short name is numeric, at most 3 chars), then pattern value.
- **Which rows are returned**: every row of service days yesterday, today and tomorrow
  (Tbilisi dates of `now`) whose `predicted >= now - pastGrace` (1 min, as the prototype).
  Yesterday is needed for its `24:xx` times; tomorrow gives the "tomorrow" section T07 shows.
- **Mapping for T07** (not implemented here): `Waiting` -> designsystem `Waiting(format(leavesAt))`,
  `Late` -> `Late(minutes = lateBy rounded up)`, `TimetableOnly` -> `TimetableOnly`,
  `NoBusYet` -> T07 decides (see 6.2).

### 3.5 Service period selection (`ServiceCalendar.kt`)

`fun List<ServicePeriod>.periodFor(date: LocalDate): ServicePeriod?`, in this order:
1. **Listed date**: periods whose `serviceDates` contain `date`. If several, the one with
   the fewest weekdays in its range, then list order. (Holidays are listed under the period
   that runs them, prototype comment "covers holidays".)
2. **Inside the listed week but unlisted**: let `window = [min, max]` of all `serviceDates`
   of all periods. If `date` is inside `window` and no period lists it, return `null`: the
   gateway told us there is no service that day. Do not fall back to the weekday.
3. **Past (or before) the listed week**: periods whose weekday range covers
   `date.dayOfWeek`; if several, fewest weekdays in range, then list order.
4. Otherwise `null` (empty service day).

Weekday range: `fromDay..toDay` by `DayOfWeek.value`; if `fromDay > toDay` it wraps
(`FRIDAY..MONDAY` covers Fri, Sat, Sun, Mon). Single days (`SUNDAY-SUNDAY`, 551 and 301)
and overlapping ranges (a `MONDAY-SATURDAY` plus a `SATURDAY-SATURDAY`) are handled by the
"fewest weekdays" rule. Periods with no `serviceDates` at all never create a window.

Why step 2: `serviceDates` "covers only the current week" (TTC_API.md); in every fixture the
listed dates of a schedule's periods together form the full week (326: 5 + 2, 551 and 301:
5 + 1 + 1, 472: 6 + 1). A date inside that week that no period lists is a day without
service, which is exactly the "empty service day" case. The prototype's own test
(`periodByDateThenWeekday`, window of one day) still passes (5.1).

### 3.6 Constants (`PredictionRules`) and why

| Name | Value | Why |
|---|---|---|
| `layoverRadiusMeters` | `500.0` | Parked fixes in the fixtures sit 0 to 6 m from the stop (1:970 x4, 1:2919, 1:20225, 1:977). Real layover buses also wait away from the stop: 301 `1:3854` at 318 m from `1:2919` and 551 `1:774` at 442 m from `1:20225`, both null/null and both the next to leave (checked against the next snapshot, TTC_API.md "Positions"). PLAN.md's ~120 m would miss both. Distance only has to say *which terminus*: the heading rule below is what keeps moving buses out (1:985 at 76 m, 1:3299 at 189 m, 1:3302 at 339 m all had a heading). 500 m covers the observed 442 m with margin and is far below any route's terminus-to-terminus distance (the shortest, 326, is ~8.9 km). The prototype's own far point (807 m) stays outside. |
| heading / next stop | both `null` required | Between trips the gateway sends both null (every parked fix). A heading with `nextStopId: null` is a bus still arriving at a last stop (551 `1:979`, 22 m) or mid-route (`1:220`, 406 m): not parked. The gateway sends **no speed** and no per-vehicle timestamp, so "speed if available" is not available; "no movement across two polls" for a bus with a stale heading is left to T10 (6.2). |
| `minTurnaround` | `2 min` | Nothing in the fixtures measures a minimum (every observed layover was 4 to 20 min). It exists so a bus that has just pulled in is never shown as leaving instantly (PLAN.md 2.0). It is applied to the bus's arrival, taken from `memory.firstSeen`, or `now` on the first poll that sees it (backlog formula `now + minimum turnaround`). On that first poll the rule can predict up to 2 min late for a bus that had been waiting long (6.2); 2 min keeps that error small and the default 1-min buffer absorbs half of it. Phase 6 learns it per route. |
| `noBusWindow` | `12 min` | Prototype `NOT_ARRIVED_WINDOW_MIN`, proven on the phone. Headways at 1:970 are 10 to 20 min, and parked buses were seen 4, 5, 17 and 19 min before their departure, so inside 12 min a bus is normally already there. |
| `lateLookback` | `10 min` | How long a still-parked bus keeps its missed departure as `Late`. At or below the shortest daytime headway at 1:970 (551, 10 min); after that the trip is treated as dropped and the bus goes back into the queue for the next departure. |
| `lateStep` | `1 min` | A `Late` bus leaves at `max(now + 1 min, firstSeen + minTurnaround)`: the time moves forward with each poll, as PLAN.md 2.0 asks. |
| `pastGrace` | `1 min` | Prototype filter `!at.isBefore(now.minusMinutes(1))`: a row does not vanish the second it passes. |
| `maxPositionsAge` | `2 min` | `RoutePositions.fetchedAt` older than this (8 missed polls at T07's 15 s) counts as no live data. |
| `maxClockSkew` | `2 min` | A `fetchedAt` up to this far after now counts as fresh (the phone clock runs behind); further ahead it counts as no live data, so one wrong clock cannot keep a snapshot fresh forever. |
| `memoryDropout` | `1 min` | A remembered bus missing from a live poll keeps its entry this long after `lastSeen` (4 polls at 15 s): the gateway sometimes leaves a parked bus out of one poll, and the bus must still be late, with its first sighting, when it comes back. Within this window the bus also holds its row (Waiting or Late) on the poll that leaves it out, unless GPS says otherwise (seen moving since, listed on another live route, or lastSeen after now). |
| `memoryMaxAge` | `30 min` | An entry last seen longer ago than this, or waiting for a departure more than `lateLookback` whole minutes past, is stale: the bus is a new sighting (`firstSeen = now`), so an old first sighting never waives the turnaround. Above the longest observed layover (20 min), far below a day. |

`DEFAULT_BUFFER_MINUTES = 1`, `MAX_BUFFER_MINUTES = 3` (PLAN.md 2.3), `MAX_WALK_MINUTES = 120`
live in `LeaveBy.kt`.

### 3.7 Algorithm (`DeparturePredictor.predict`)

```
now = clock.nowInTbilisi(); today = now.toLocalDate()
dates = [today - 1, today, today + 1]
for each RouteSnapshot r:
  rows = for each schedule s in r.schedules: s.departuresAt(stop.id, dates)
  if no schedule of r servesStop(stop.id) in any period: missingTimetables += r.route.id; continue
  live = r.positions != null && age(r.positions.fetchedAt, now) <= maxPositionsAge
  terminusPatterns = patterns with at least one row where atFirstStop
  parked = if live: r.positions.vehicles.filter { it.isInLayoverAt(stop.location, rules) } else empty
  a vehicle id listed twice keeps one entry, the one whose pattern starts here
  memory entries are looked up by (route id, vehicle id); stale entries (3.6) count as none
  for each parked v: target pattern = v.pattern if it is in terminusPatterns,
      else its remembered pattern if that is in terminusPatterns,
      else the terminusPattern whose next open row is earliest (the gateway relabels buses
      while they wait, TTC_API.md), else ignore v (stop is no pattern's first stop)
  held: a remembered, not stale entry of the route whose vehicle is missing from the poll
      altogether (not merely unparked) and 0 <= now - lastSeen <= memoryDropout is still parked:
      it joins the queues with its remembered pattern, firstSeen and waitingFor, and gets
      a row by the same rules as a seen bus, so its row does not flicker for one poll.
      GPS wins over memory, so an entry is never held when:
        - its vehicle id is listed (parked or not) on ANY live route of this request; an
          offline or stale route lists nothing. This skips the hold for that poll only; the
          entry is kept unchanged, since the id on another route may be another bus
        - the entry is marked seenMoving: its bus was listed on this route since lastSeen but
          not parked here, so it has left. The mark is cleared only when the bus is seen
          parked here again
        - lastSeen is after now (the clock moved back): no measure of a dropout
  for each terminus pattern P (rows at the first stop, sorted by scheduled):
      queue = parked for P sorted by (memory.waitingFor ?: MAX, memory.firstSeen ?: now, vehicleId.value)
      1. Late: v in queue whose memory says (route, P, waitingFor = D), D in [now - lateLookback, now),
         and an unclaimed row with scheduled == D exists -> that row is
         Late(v, leavesAt = max(now + lateStep, firstSeen + minTurnaround), lateBy = leavesAt - D)
      2. Waiting: remaining queue in order, each takes the earliest unclaimed row with scheduled >= now:
         Waiting(v, leavesAt = max(scheduled, (memory.firstSeen ?: now) + minTurnaround))
      3. NoBusYet: if live, the first row with scheduled >= now is unclaimed and
         scheduled - now <= noBusWindow
      every other row: TimetableOnly, predicted = scheduled
  rows not at a first stop: TimetableOnly (v1 has no downstream propagation; T10)
  board hint: row of board with routeShortName == r.route.shortName and
      row.pattern == P, attached to the first row with scheduled >= now of that pattern;
      a board row with pattern == null goes on the route's single first row with
      scheduled >= now, unless a pattern row already took it; never read anywhere else
memory' = for each live route: its parked vehicles -> (routeId, vehicleId) to ParkedVehicle(P,
      firstSeen = old.firstSeen ?: now.toInstant(), waitingFor = scheduled of the row it got, or null,
      lastSeen = now); a held vehicle is written the same way but keeps its old lastSeen, so
      dropout polls never stretch the window;
  entries of routes without live data this call are kept unchanged (an offline poll does
  not erase history); an entry of a vehicle no longer parked is kept unchanged while it is
  not stale and 0 <= now - lastSeen <= memoryDropout, then dropped; if the vehicle is listed
  on this route but not parked here, the kept entry is marked seenMoving = true
departures = all rows, predicted >= now - pastGrace, sorted (3.4)
```

`departuresAt(stopId, dates)`: for each date, `periodFor(date)`; in that period take every
`ScheduledStop` with `stopId`; **skip an entry at the period's highest position when the
period has more than one stop** (those times are arrivals at the end of the line: 326
`1:01` lists `1:970` at position 45 of 45 with `24:02`, which is not a departure from
1:970). A stop listed twice (loop) gives one row per entry. Each time becomes
`ScheduledDeparture(routeId, pattern, stopId, serviceDate = date, scheduled = time.atDate(date), atFirstStop = entry.position == lowest position)`.
`ServiceMinute.atDate` already handles `24:05` as 00:05 on the next calendar day.

`LayoverMemory`:
```kotlin
data class LayoverMemory(val vehicles: Map<ParkedKey, ParkedVehicle>) { companion object { val Empty = LayoverMemory(emptyMap()) } }
data class ParkedKey(val routeId: RouteId, val vehicleId: VehicleId)
data class ParkedVehicle(val pattern: PatternSuffix, val firstSeen: Instant, val waitingFor: ZonedDateTime?, val lastSeen: Instant = firstSeen, val seenMoving: Boolean = false)
```
A memory entry whose `firstSeen` is after `now` (clock moved back) is treated as `now`.

Invariants the tests enforce (5.4): a `Waiting` departure is never earlier than its
timetable time nor earlier than now (a bus never leaves a first stop early and is never
"arriving now"); each vehicle serves at most one row; `TimetableOnly` and `NoBusYet` rows
have `predicted == scheduled`; the board never changes a time.

### 3.8 Leave-by (`LeaveBy.kt`)

```kotlin
const val DEFAULT_BUFFER_MINUTES = 1
fun PredictedDeparture.leaveBy(walkMinutes: Int, bufferMinutes: Int = DEFAULT_BUFFER_MINUTES): ZonedDateTime =
    predicted.minusMinutes(walkMinutes.coerceIn(0, MAX_WALK_MINUTES).toLong() + bufferMinutes.coerceIn(0, MAX_BUFFER_MINUTES))
data class LeaveOption(val departure: PredictedDeparture, val leaveBy: ZonedDateTime)
data class LeavePlan(val best: LeaveOption?, val fallback: LeaveOption?)
fun List<LeaveOption>.planFrom(now: ZonedDateTime): LeavePlan
```
- Leave-by uses `predicted` (so a waiting bus uses its `leavesAt`, a late bus its moving time).
- Values are coerced, not `require`d: they come from DataStore (T04) and a bad stored value
  must not crash the Now screen.
- `planFrom`: catchable = `leaveBy >= now` (equal counts). `best` = catchable option with the
  earliest `leaveBy` (ties: earliest `predicted`); `fallback` = the next catchable option
  after `best` in the same order. Both null when nothing is catchable. Walk minutes are per
  stop, so T07 builds `LeaveOption`s per saved stop and merges them.

### 6.2 Open questions and things to watch

- **Radius 500 m vs PLAN.md's ~120 m.** Justified by two real lay-by buses (318 m, 442 m);
  the risk is an off-duty null/null bus parked in a depot within 500 m of a first stop
  being counted as waiting. Effect is limited: the row is a timetable time either way; only
  the chip changes and `NoBusYet` is suppressed. Watch it at 1:970 during T07's live check.
- **First-poll turnaround.** On the first poll that sees a bus (no memory), `leavesAt` is at
  least `now + 2 min`, so a bus that had been waiting long and leaves within 2 min is shown
  up to 2 min late (the unsafe side for the rider). Memory fixes it from the second poll
  only in the sense that `firstSeen` stays fixed; the manager may prefer "no floor without
  memory" (then `max(scheduled, now)`). The backlog formula is followed as written.
- **Which bus leaves first is not knowable** from one snapshot: in both lay-by cases the bus
  away from the stop left before the one on it. v1 orders by memory, then vehicle id; only
  the vehicle id shown on a row can be wrong, never the time. T12 ("open that bus") should
  treat the id as a best guess.
- **No stationarity check.** A bus parked with a stale heading is not detected. Needs two
  polls of positions (T10 or later).
- **`NoBusYet` has no designsystem chip.** T06 has `Waiting`, `Live`, `Late`,
  `TimetableOnly`. T07 must either show it as `TimetableOnly` or add a "no bus yet" chip and
  string (en + ka). Flag to the user in T07.
- **Serviced dates on a mid-week fetch.** All fixtures were recorded on a Monday, where the
  listed dates form the full week. If a Wednesday fetch lists only Wednesday to Sunday, the
  window shrinks and Monday/Tuesday fall back by weekday, which is still correct. Confirm with
  a fresh `tools/record-fixtures.sh` run when convenient (not done here: this plan did not
  use the key).
- **PLAN.md "38 minutes"** (T03 follow-up): the derived 326 case uses 17:32 -> 17:49 (17 min),
  consistent with the 18-minute weekday headway. Not changed by T05; still for the user.
- **Missing timetable with a parked bus**: v1 lists nothing for that route (no time to
  anchor on). T07 can show "timetable unavailable" from `missingTimetables`.
- **Kover** on Gradle 9.8 and Kotlin 2.4.20 is untested here; step 10 is droppable. CI runs
  `test`, not `koverVerify`, so the 90 % rule is local only until CI is extended (follow-up).
- **Detekt** defaults (`CyclomaticComplexMethod` 15, `LongMethod` 60, `ReturnCount` 2,
  `NestedBlockDepth` 4): keep `predict` a short pipeline of private functions; split
  terminus assignment into its own file if needed. `MagicNumber` is off in tests and for
  property declarations, so constants live in `PredictionRules`.
- **Board join by short name**: board rows have no route id; metro and cable car numbers
  restart at 1, so a board row `1` could match two routes. Also compare `kind` when the
  route is metro or cable car (board `vehicleMode` says `SUBWAY`/`GONDOLA`); buses and
  minibuses both say `BUS` and have unique numbers. It only affects a hint.
