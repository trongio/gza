# T02 Gateway config and key rotation: implementation plan

Branch: `task/T02-gateway-config`. Gateway and Firebase facts checked live on
**2026-09-28** with curl (now recorded in `docs/TTC_API.md`, sections "Access" and
"Remote Config (runtime key)"). Versions checked the same day on Maven Central.

## 1. Goal

Give the app a gateway key that survives rotation. `:core:ttc` (pure JVM) gets a config
chain that returns the current `PIS_GATEWAY_KEY` and `PIS_GATEWAY_BASE_URL`: a fresh
cached value first, otherwise a runtime fetch from TTC's Firebase Remote Config
(Installations REST, then Remote Config fetch REST, exactly as
`tools/fetch-ttc-config.sh` does), otherwise the stale cache, otherwise the build-time
`TtcFallbackConfig` from `ttc.properties`. The cache sits behind an interface with an
in-memory implementation now, so T04 can back it with DataStore. An OkHttp interceptor
rewrites gateway requests onto the configured base URL, adds `x-api-key`, and on a 401 or
403 refetches the key at most once (single-flight across parallel requests) and retries
the request exactly once. `:app` wires two OkHttp clients with Hilt (Firebase and
gateway) and a debug-only logging interceptor that redacts every secret header. Proven by
MockWebServer unit tests; no UI changes.

## 2. Acceptance criteria

| Backlog criterion | Proven by |
|---|---|
| Unit tests with MockWebServer: first launch fetch | `GatewayAuthInterceptorTest.first launch fetches remote config then calls the gateway with the remote key` (empty cache: one Installations POST, one Remote Config fetch, then the gateway GET carries the remote key on the remote base URL; the config is written to the cache). |
| ... cached reuse | `GatewayAuthInterceptorTest.second request reuses the cached key without firebase calls` and `GatewayAuthInterceptorTest.new provider over a warm cache skips firebase` (simulates a process restart with the same cache), plus `cache older than the ttl is refetched`. |
| ... 401 then refetch then success | `GatewayAuthInterceptorTest.401 refetches the key once and retries with the new key` (cached key `old` gets 401, Remote Config now serves `new`, retry gets 200, caller sees 200, exactly 2 gateway requests and 1 Remote Config fetch). Also `403 is handled like 401` and `parallel 401s trigger a single refetch and every request retries once`. |
| ... Remote Config down so fallback used | `GatewayAuthInterceptorTest.remote config down uses the build time fallback key` (Firebase answers 503) and `remote config unreachable uses the build time fallback key` (Firebase MockWebServer closed, connection refused). |
| Key never logged (test asserts the logging interceptor redacts the header) | `TtcHttpLoggingTest.gateway key header is redacted in the log`, `firebase api key and installation tokens are never logged`, `logging never goes beyond headers`, plus `RedactionTest` for every `toString()` and exception message that could carry a secret. `:app` `NetworkModuleTest.logging comes after auth so it sees and redacts the key header` and `release builds add no logging interceptor`. |

All run in `./gradlew test` (JUnit 5), so CI proves them on every PR.

### 3.3 Data shapes

```kotlin
enum class ConfigSource { REMOTE, CACHE, STALE_CACHE, FALLBACK }

/** What the interceptor uses. [generation] increases on every activation inside one provider. */
class GatewayConfig(
    val baseUrl: HttpUrl,          // e.g. https://transit.ttc.com.ge/pis-gateway (no /api)
    val apiKey: String,
    val source: ConfigSource,
    val fetchedAt: Instant?,       // null for FALLBACK
    val generation: Long,
) {
    fun sameCredentialsAs(other: GatewayConfig) = apiKey == other.apiKey && baseUrl == other.baseUrl
    override fun toString() = "GatewayConfig(baseUrl=$baseUrl, apiKey=<redacted>, source=$source, " +
        "fetchedAt=$fetchedAt, generation=$generation)"
}

data class GatewayConfigPolicy(
    val ttl: Duration = Duration.ofHours(12),               // Firebase SDK default fetch interval
    val minForcedRefreshInterval: Duration = Duration.ofSeconds(60),
    val failureBackoffInitial: Duration = Duration.ofMinutes(1),
    val failureBackoffMax: Duration = Duration.ofHours(1),
    val requireHttpsBaseUrl: Boolean = true,                // tests pass false (MockWebServer is http)
)

class GatewayConfigUnavailableException(message: String) : IOException(message)

// Persisted shapes. Plain strings and Instants so the T04 DataStore can store them as-is.
data class CachedGatewayConfig(val baseUrl: String, val apiKey: String, val fetchedAt: Instant)   // redacting toString
data class FirebaseInstallation(
    val fid: String, val refreshToken: String, val authToken: String, val authTokenExpiresAt: Instant,
)                                                                                               // redacting toString

interface TtcConfigCache {
    suspend fun readConfig(): CachedGatewayConfig?
    suspend fun writeConfig(config: CachedGatewayConfig)
    suspend fun readInstallation(): FirebaseInstallation?
    suspend fun writeInstallation(installation: FirebaseInstallation?)   // null clears it
}
```

`InMemoryTtcConfigCache` holds two `@Volatile` fields (writes are already serialized by
the provider mutex and the client, reads of a single reference are atomic). T04 adds
`DataStoreTtcConfigCache` in `:core:data` and rebinds the interface; nothing else changes.
Keeping `fid` and tokens in the same store means a restart reuses the installation
instead of registering a new one in TTC's Firebase project every launch.

`GatewayKeys.isUsableApiKey(key)`: non-blank, length <= 256, every char in `0x21..0x7E`.
This matters: `Request.Builder.header()` throws `IllegalArgumentException` on control or
non-ASCII characters, which inside an interceptor would crash the call instead of failing
it. Applied to remote, cached and fallback keys alike; an unusable key is treated as
absent.

`GatewayKeys.parseBaseUrl(raw, requireHttps)`: `raw.trim().toHttpUrlOrNull()`, rejected if
null, if `requireHttps` and scheme is not https, or if it has a query or fragment. Remote
and cached base URLs that fail fall back to the fallback base URL (with the remote key);
a fallback base that fails uses `TtcGateway.DEFAULT_BASE_URL`
(`https://transit.ttc.com.ge/pis-gateway`, same default as the build plugin).

### 3.4 Base URL: placeholder host, rewritten per request

Retrofit (T03) needs a base URL at construction, but the real one comes from Remote
Config at runtime. Decision: T03 builds Retrofit with
`TtcGateway.PLACEHOLDER_BASE_URL = "https://ttc-gateway.invalid/"` and declares paths as
`api/v2/stops/{id}`. `GatewayAuthInterceptor` rewrites every request whose host is
`ttc-gateway.invalid` onto the active `GatewayConfig.baseUrl`:

`GatewayUrls.resolve(url, base)`: start from `base.newBuilder()`, drop a trailing empty
path segment of the base (`.../pis-gateway/` and `.../pis-gateway` must give the same
result), append every `url.encodedPathSegments` with `addEncodedPathSegment` (keeps
`1:970` and `%20` exactly as encoded), copy `url.encodedQuery`. Reasons:
- The key can only ever be sent to the configured gateway. Requests to any other host
  pass through the interceptor untouched and **without** the key, so a mistake in T03
  (or a Firebase call routed through the wrong client) cannot leak it.
- `.invalid` is reserved (RFC 2606), so an unrewritten request fails loudly with an
  `UnknownHostException` instead of silently hitting a wrong server.
- Tests point the gateway at MockWebServer by making Remote Config (or the fallback)
  return `server.url("/pis-gateway")`, with `requireHttpsBaseUrl = false`.

### 3.5 Firebase client (`FirebaseRemoteConfigClient : RemoteGatewayConfigSource`)

Constructor: `(httpClient: OkHttpClient /* the Firebase client, never the gateway one */,
endpoints: FirebaseEndpoints, credentials: FirebaseWebCredentials, cache: TtcConfigCache,
clock: Clock, ioDispatcher: CoroutineDispatcher, json: Json = TtcJson,
newFid: () -> String = FirebaseInstallationIds::generate)`.

`FirebaseEndpoints.Production` = `https://firebaseinstallations.googleapis.com/` and
`https://firebaseremoteconfig.googleapis.com/`. Tests pass `server.url("/")` for both.
Project id is added with `addPathSegment` (encoded); the literal suffixes
`installations`, `authTokens:generate`, `namespaces`, `firebase:fetch` with
`addPathSegment` too (OkHttp does not encode `:` in path segments; the tests assert the
exact recorded path, so any encoding change fails loudly).

`suspend fun fetch(): RemoteGatewayConfig` runs in `withContext(ioDispatcher)`:
1. If `!credentials.isComplete` (any field blank): throw `RemoteConfigException(NOT_CONFIGURED)` with no network call.
2. `installation = installationOrNull()`:
   - stored = `cache.readInstallation()`. If stored and `authTokenExpiresAt > now + 1 h`, use it.
   - If stored but token expiring: `POST {installations}/v1/projects/{p}/installations/{fid}/authTokens:generate`
     with `Authorization: FIS_v2 <refreshToken>`, body `{"installation":{"sdkVersion":"w:0.6.4","appId":...}}`.
     200: store the new token and expiry, use it. 401 or 404: clear it and register anew.
     Any other failure: use stored if its token has not expired yet, else no installation.
   - No usable installation: `POST .../installations` with body
     `{"fid":newFid(),"appId":...,"authVersion":"FIS_v2","sdkVersion":"w:0.6.4"}`. 200: store
     using the **returned** `fid` (the server replaces malformed ids). Any failure: `null`.
   - Installations failing is never fatal: live data shows Remote Config does not enforce
     the token today (TTC_API.md), so step 3 still runs.
3. `POST {remoteConfig}/v1/projects/{p}/namespaces/firebase:fetch`, body
   `{"appInstanceId": installation?.fid ?: newFid(), "appInstanceIdToken": installation?.authToken (omitted when null),
   "appId":...,"sdkVersion":"0.4.0","languageCode":"en-US"}`.
4. Parse `{entries?: Map<String,String>, state?: String, templateVersion?: String}`.
   `apiKey = entries["PIS_GATEWAY_KEY"]?.trim()`, must pass `isUsableApiKey` else
   `MISSING_KEY` (covers `NO_TEMPLATE`, `EMPTY_CONFIG`, missing entries) or `MALFORMED`
   (present but unusable). `baseUrl = entries["PIS_GATEWAY_BASE_URL"]` (raw, validated by the provider).

Headers on every Firebase call: `x-goog-api-key: <apiKey>` (**header, never the `?key=`
query**: verified to work, and it keeps the key out of URLs and URL-logging),
`Content-Type: application/json`, `Accept: application/json`. `expiresIn` like
`"604800s"` or `"3.5s"` is parsed as decimal seconds; unparseable counts as 0 (token
treated as expired next time).

Error mapping (`RemoteConfigException(reason, httpCode: Int? = null, googleStatus: String? = null, cause)`):

| Situation | Reason |
|---|---|
| blank credentials | `NOT_CONFIGURED` |
| `IOException` (refused, DNS, `SocketTimeoutException`, `InterruptedIOException` from `callTimeout`) | `NETWORK` |
| non-2xx | `HTTP`, with `httpCode` and `googleStatus` parsed from `{"error":{"status":...}}` if possible |
| `SerializationException` / `IllegalArgumentException` while decoding | `MALFORMED` |
| 200 but no usable `PIS_GATEWAY_KEY` | `MISSING_KEY` |

Messages are built only from `reason`, `httpCode`, `googleStatus`: never from a response
body, URL or header (the fetch body contains the gateway key). `RemoteConfigException`
extends `Exception`, not `IOException`, so it never escapes an interceptor by accident.
Catch only the specific types above (detekt `TooGenericExceptionCaught`); never catch
`CancellationException`.

`FirebaseInstallationIds.generate(random: java.util.Random = SecureRandom())`: the
Firebase JS algorithm: 17 random bytes, `bytes[0] = 0x70 or (bytes[0] and 0x0F)`,
url-safe base64 without padding, first 22 chars. Always starts with `c`..`f`.

### 3.6 Config chain (`DefaultGatewayConfigProvider : GatewayConfigProvider`)

```kotlin
interface GatewayConfigProvider {
    /** Fresh active config or null. Never blocks, never does I/O: the interceptor's fast path. */
    fun peek(): GatewayConfig?
    /** Cache, then remote, then stale cache, then fallback. Throws GatewayConfigUnavailableException. */
    suspend fun current(): GatewayConfig
    /** Called after [rejected] got 401/403. Returns a config with different credentials to retry with, or null. */
    suspend fun refreshAfterRejection(rejected: GatewayConfig): GatewayConfig?
}
```

Constructor: `(cache: TtcConfigCache, remote: RemoteGatewayConfigSource,
fallback: TtcFallbackConfig, clock: Clock, policy: GatewayConfigPolicy = GatewayConfigPolicy())`.
No dispatcher here: the only blocking I/O is inside the client, which has its own injected
dispatcher; cache implementations own theirs.

State (all mutated only under `mutex`, the two read by `peek()` are `@Volatile`):
`active: GatewayConfig?`, `nextRemoteAttemptAt: Instant` (initially `Instant.MIN`),
`consecutiveFailures: Int`, `lastForcedRefreshAt: Instant?`, `generation: Long`.

Freshness (`isFresh(config, now)`):
- `REMOTE` / `CACHE`: `now < fetchedAt + ttl`.
- `STALE_CACHE` / `FALLBACK`: `now < nextRemoteAttemptAt` (they are only good until the
  backoff allows the next remote attempt).

`peek() = active?.takeIf { isFresh(it, clock.instant()) }`.

`current() = peek() ?: mutex.withLock { peek() ?: load() }` (double-checked, so 50 parallel
callers on a cold start cause exactly one remote fetch).

`load()`:
1. If `active == null`: read `cache.readConfig()`; if usable and fresh, activate it as `CACHE` and return.
   Keep it as `staleCandidate` otherwise.
2. If `now < nextRemoteAttemptAt` (in backoff): return `staleOrFallbackOrThrow()`.
3. `remote.fetch()`:
   - success: build `REMOTE` config (`fetchedAt = now`), `cache.writeConfig(...)`,
     `consecutiveFailures = 0`, `nextRemoteAttemptAt = Instant.MIN`, activate, return.
   - `RemoteConfigException`: `consecutiveFailures++`,
     `nextRemoteAttemptAt = now + min(initial * 2^(failures-1), max)`, return `staleOrFallbackOrThrow()`.

`staleOrFallbackOrThrow()`, in order: the current `active` REMOTE/CACHE/STALE_CACHE
config (re-activated as `STALE_CACHE`), the `staleCandidate` from the cache (as
`STALE_CACHE`), the fallback (as `FALLBACK`, if `fallback.gatewayKey` is usable), else
throw `GatewayConfigUnavailableException("No gateway key: Remote Config failed and no build-time fallback")`.
Why stale beats fallback: a key fetched from Remote Config is newer than the one baked
at build time; if it has since rotated, the 401 path fixes it. The fallback is never
written to the cache, so the next launch tries Remote Config again.

`refreshAfterRejection(rejected)` under `mutex`:
1. `a = active`. If `a != null && a.generation != rejected.generation && !a.sameCredentialsAs(rejected)`:
   another request already refreshed; return `a` (no network).
2. If `lastForcedRefreshAt != null && now < lastForcedRefreshAt + minForcedRefreshInterval`:
   return `null` (cooldown: a key that is really dead cannot cause a refetch per request).
3. `lastForcedRefreshAt = now`; `remote.fetch()` ignoring the backoff gate (a 401 is strong
   evidence of rotation).
   - success: write cache, reset backoff, activate as `REMOTE`; return it if
     `!sameCredentialsAs(rejected)`, else `null` (same key: the 401 is not a rotation, do not retry).
   - failure: bump the backoff as in `load()`; if the fallback key is usable and differs
     from `rejected`, activate and return it as `FALLBACK`; else `null`.

`activate(config)` assigns `generation = ++generation` and sets `active`.

Concurrency summary: one `Mutex` serializes all loads and refreshes. Parallel 401s all
carry the same `rejected.generation`; the first one refetches, the rest wait on the mutex,
then see a newer generation with different credentials and retry with it without any
network call. Late 401s (arriving after the cooldown started, with the same generation)
get `null`. There is no loop anywhere: see 3.7.

### 3.7 Interceptor (`GatewayAuthInterceptor(provider)`, an application interceptor)

```kotlin
override fun intercept(chain: Interceptor.Chain): Response {
    val request = chain.request()
    if (request.url.host != TtcGateway.PLACEHOLDER_HOST) return chain.proceed(request)   // never add the key elsewhere
    val config = provider.peek() ?: runBlocking { provider.current() }                  // throws GatewayConfigUnavailableException (IOException)
    val first = chain.proceed(request.authorizedWith(config))
    if (first.code != 401 && first.code != 403) return first
    if (request.body?.isOneShot() == true) return first
    val retryWith = runBlocking { provider.refreshAfterRejection(config) } ?: return first
    first.close()
    return chain.proceed(request.authorizedWith(retryWith))                              // returned whatever its code
}
```
- `authorizedWith(c)` = `newBuilder().url(GatewayUrls.resolve(url, c.baseUrl)).header("x-api-key", c.apiKey).build()`.
- **Exactly one retry**: the retry is a straight-line second `proceed`, no loop, no
  recursion, and it is an application interceptor so the retry does not pass through
  itself again. A second 401 goes back to the caller.
- `runBlocking` is acceptable here: OkHttp interceptors are synchronous and run on OkHttp's
  own threads (Retrofit suspend calls use `enqueue`). The fast path (`peek()`) avoids it
  on every request except the first after a TTL expiry. Firebase calls go through a
  different `OkHttpClient` with `execute()`, so there is no re-entry into this interceptor
  and no dispatcher starvation.
- 400, 404, 5xx: returned untouched, no refresh (a missing key is 400 on this gateway,
  but the interceptor never sends a blank key because of `isUsableApiKey`).

### 3.8 HTTP clients, timeouts, logging

`TtcHttpClients` (in `:core:ttc`, so it is tested without Android):
- `firebaseClient(base: OkHttpClient, logging: Interceptor?)`: `base.newBuilder()`,
  connect 5 s, read 10 s, write 10 s, call 15 s; add `logging` if non-null.
- `gatewayClient(base, auth: GatewayAuthInterceptor, logging: Interceptor?)`:
  connect 10 s, read 20 s, write 20 s, call 60 s (covers a cold config fetch, two
  Firebase calls of up to 15 s each, plus one retry); `addInterceptor(auth)` then
  `addInterceptor(logging)`. Order matters: logging after auth sees the final URL and the
  `x-api-key` header, so the redaction is actually exercised, and it logs the retry too.
- Both come from one `base` via `newBuilder()` so they share the connection pool and dispatcher.

`TtcHttpLogging.interceptor(logger: HttpLoggingInterceptor.Logger)`: level `HEADERS`,
`redactHeader("x-api-key")`, `redactHeader("x-goog-api-key")`,
`redactHeader("Authorization")`, `redactQueryParams("key")`. Never `BODY`: the Remote
Config response body contains the gateway key and the Installations body contains tokens,
and gateway bodies are large (2,753 stops). Constant `TtcHttpLogging.REDACTED_HEADERS`
lists the three headers so tests iterate it.

### 3.9 Hilt wiring in `:app`

`app/src/main/kotlin/ge/hackerman/gza/di/`:
- `CoroutinesModule.kt`: `@Qualifier annotation class IoDispatcher`;
  `@Provides @IoDispatcher fun provideIoDispatcher(): CoroutineDispatcher = Dispatchers.IO`.
  (T04 may move the qualifier to a shared module when `:core:data` needs it; `:core:ttc`
  stays DI-free.)
- `NetworkModule.kt`: qualifiers `@FirebaseHttp`, `@GatewayHttp`, and:
  - `provideBaseOkHttpClient(): OkHttpClient` (plain `OkHttpClient()`), `@Singleton`.
  - No nullable logger binding (Hilt cannot provide `null` cleanly). Instead the two
    clients are provided by calling plain `internal` functions that tests can drive:
    `buildFirebaseClient(base, debug: Boolean, logger)` and
    `buildGatewayClient(base, auth, debug: Boolean, logger)`, called with
    `BuildConfig.DEBUG` and `HttpLoggingInterceptor.Logger { Log.d("GzaHttp", it) }`.
    When `debug` is true they pass `TtcHttpLogging.interceptor(logger)` to
    `TtcHttpClients`, otherwise `null`.
  - `provideFirebaseCredentials(fallback: TtcFallbackConfig) = fallback.firebaseCredentials()`.
  - `provideTtcConfigCache(): TtcConfigCache = InMemoryTtcConfigCache()` `@Singleton`
    (T04 replaces this binding).
  - `provideRemoteGatewayConfigSource(@FirebaseHttp client, credentials, cache, clock, @IoDispatcher io): RemoteGatewayConfigSource`
    = `FirebaseRemoteConfigClient(client, FirebaseEndpoints.Production, ...)` `@Singleton`.
  - `provideGatewayConfigProvider(cache, remote, fallback, clock): GatewayConfigProvider`
    = `DefaultGatewayConfigProvider(...)` `@Singleton`. **Must be a singleton**: the
    mutex and generation only work if every request shares one instance.
  - `provideGatewayAuthInterceptor(provider)` and the `@GatewayHttp OkHttpClient` `@Singleton`.
- `build-logic/.../HiltConventionPlugin.kt`: add the KSP arg
  `dagger.fullBindingGraphValidation=ERROR`. Nothing injects the network graph until T03,
  so without it a broken binding would compile; with it Dagger validates every module.

Release builds: no logging interceptor at all (not level `NONE`, simply absent).

## 6. Risks / open questions

1. **Remote Config does not enforce the installation token today.** We still register an
   installation to behave like the real web client; if Installations starts failing, the
   fetch proceeds without a token. If Google starts enforcing it, the code path already
   sends the token, so nothing changes.
2. **Firebase web credentials are baked in at build time.** The script scrapes them from
   the TTC page; the app does not. If TTC rotates the Firebase API key or app id, Remote
   Config fails with 400/403 and the app lives on the cached or fallback key until a
   rebuild. Follow-up for the backlog: scrape `firebaseCredentials` from the page at
   runtime as a further fallback.
3. **In-memory cache until T04.** Every cold start fetches Remote Config and registers a
   new installation. Acceptable for T02; T04's DataStore store must also exclude the key
   and tokens from backup (`backup_rules.xml`, `data_extraction_rules.xml`): an
   installation restored onto another device would share its fid.
4. **`runBlocking` in the interceptor.** Safe on OkHttp threads. If someone ever calls the
   gateway client with `execute()` from a single-threaded coroutine dispatcher the thread
   blocks for up to 30 s during a cold config fetch; T03 must use Retrofit suspend
   functions (which enqueue), never `execute()` on the main thread.
5. **detekt defaults.** `ReturnCount` (max 2) will fire on `load()` / `refreshAfterRejection`
   / `intercept`: restructure with `when` or small helpers rather than suppressing; if a
   guard-clause style is clearly more readable, a local `@Suppress("ReturnCount")` with a
   why-comment is acceptable. Also watch `TooGenericExceptionCaught`, `SwallowedException`
   (the catch in `installationOrNull()` must be deliberate: add a comment), `MagicNumber`
   (timeouts and `0x70` as named constants).
6. **Flaky concurrency test.** The latch-based gateway dispatcher makes the ordering
   deterministic; give every latch and `takeRequest` a timeout (5 s) so a bug fails fast
   instead of hanging CI. MockWebServer serves each HTTP/1.1 connection on its own
   thread, so a blocking dispatcher is fine.
7. **`:` in paths.** OkHttp leaves `:` unencoded in path segments; `firebase:fetch`,
   `authTokens:generate` and `1:970` rely on that. The tests assert exact paths.
8. **OkHttp 5 on Android.** `okhttp` resolves to its Android variant in `:app` through
   Gradle module metadata and to the JVM variant in `:core:ttc`; no action, but if lint
   complains about duplicate classes check `./gradlew :app:dependencies`.
9. **Full binding graph validation** may surface an existing Hilt issue in `:app`. Fix it;
   do not drop the flag. If KSP rejects the option name, report it in the PR.
   Outcome: KSP accepts `dagger.fullBindingGraphValidation=ERROR` and it does validate the
   network graph in `NetworkModule` even though nothing injects it yet. No deviation.
10. **Secrets.** Never print, `cat` or `Read` `ttc.properties` or generated `BuildConfig`.
    Fixtures use sentinel strings only. `tools/check-no-secrets.sh` must pass.
    Remote Config response bodies (which contain the real key) must never be saved as
    fixtures by `tools/record-fixtures.sh` in T03.
11. **Open question for the manager:** should the Settings screen (later) show the config
    source (remote, cached, fallback)? The provider does not expose a `Flow` for it yet;
    adding `val source: StateFlow<ConfigSource?>` later is cheap.

## 7. Changes after review (fix round 1)

These supersede the matching parts of section 3.

- **No redirects on the gateway client** (3.8). `TtcHttpClients.gatewayClient` sets
  `followRedirects(false)` and `followSslRedirects(false)`: OkHttp strips only
  `Authorization` on a cross-host redirect, so a followed 3xx would carry `x-api-key` to
  the `Location` host. The caller gets any 3xx as is, same host included.
- **Stale while revalidate** (3.6). `DefaultGatewayConfigProvider` takes a
  `refreshScope: CoroutineScope` (`:app` binds a process-wide `@ApplicationScope`
  `SupervisorJob() + @IoDispatcher` scope). `current()`: fresh active config returns at
  once; an active config that is due (TTL or backoff over) also returns at once and
  starts at most one background `load()` on `refreshScope`; only a cold start with no
  active config waits on the mutex. A cold start over an expired cache activates it as
  `STALE_CACHE` and refreshes behind it. `refreshAfterRejection` still waits on the mutex,
  so a 401 during a background refresh waits for it and retries with its result.
- **Freshness** (3.6): `fetchedAt != null && !fetchedAt.isAfter(now) &&
  Duration.between(fetchedAt, now) < ttl`, so a future `fetchedAt` (clock moved back) is
  stale and `Instant.MAX` cannot overflow.
- **Interceptor** (3.7): the 401 response is closed if `refreshAfterRejection` throws, and
  after each blocking section a cancelled call throws `IOException("Canceled")` instead of
  proceeding (`runBlocking` itself does not see `Call.cancel()`).
- **Firebase headers** (3.5): `FirebaseRest` builds the request inside its `try`; an
  `IllegalArgumentException` from a header value becomes `MALFORMED` without a cause
  (OkHttp quotes the value). Refresh tokens must pass `GatewayKeys.isHeaderSafe`
  (non-empty visible ASCII), both when parsed and when read back; an unsafe stored one is
  cleared and the app registers anew.

## 8. Changes after review (fix round 2)

- **Any failure is a failed attempt** (3.6). `fetchRemote` treats every non-cancellation
  exception from `remote.fetch()` as a failed fetch (backoff, then stale cache or
  fallback). A `CancellationException` the source throws while the caller is still active
  (an inner timeout) counts as a failure too. `cache.readConfig()` failing is a cache
  miss; `cache.writeConfig()` is best effort and the fetched key is activated anyway.
  Unexpected failures are logged with `java.util.logging`, class name only.
- **Background refresh** (3.6). The job rethrows only cancellation; any other exception
  is logged by class name and counted as a remote failure under the mutex. The
  `@ApplicationScope` scope has a `CoroutineExceptionHandler` that logs the class name,
  as a safety net against a process crash.
- **Interceptor** (3.7). Anything the provider throws that is not an `IOException` is
  wrapped in one, because OkHttp rethrows other exceptions on its dispatcher thread.
- **Tests**. `RefreshScope` records uncaught throwables and rethrows them from
  `awaitRefreshes()` and `close()`. The edge case "rejected response is closed when the
  refetch throws" can no longer use a throwing cache write (that now succeeds and
  retries), so it uses a provider whose refresh throws; a new test covers the retry.
