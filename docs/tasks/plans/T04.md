# T04 Local data layer and sync: implementation plan

Branch: `task/T04-data-layer` (from `main` with T01, T02, T03, T06). T05 (prediction engine)
is being built in parallel in `:core:predict` and `:core:model`; see 6.1 for the files both
tasks touch. Versions were checked on Google Maven and Maven Central on 2026-09-30.

## 1. Goal

Add `:core:data`, the app's single source of truth. Room holds the transit catalog (stops,
routes) and, per route, its patterns, stop order, polylines and timetables; typed DataStore
files hold the user's preferences (saved stops with walk minutes and route filters, buffer)
and the gateway config plus Firebase installation (replacing T02's in-memory cache).
Repositories expose cold `Flow`s read from Room, wrapped in a small status type the UI can
show (fresh, stale but cached, offline with no data). The network only refreshes Room: the
catalog on first launch and weekly through a unique periodic `@HiltWorker`, a route's data
on first use and again on app open when older than 12 h. A sync that returns nothing, is
malformed, or fails half way never replaces good cached data, so after one online launch
the app keeps working offline. T02 and T03 follow-ups that name T04 are closed here, and
backup rules are revisited: favourites are backed up, the cache and the key are not.

`[versions]` gets `room3 = "3.0.3"`; the `room = "2.8.5"` version and the three
`androidx-room-*` libraries are deleted (nothing references them: check with
`rg 'androidx.room\b|libs.androidx.room\.' --glob '*.kts'` first). The root
`build.gradle.kts` gets `alias(libs.plugins.room3) apply false`.

**Decision: Room 3, not Room 2.8.** Room 3.0.0 went stable on 2026-07-01 (3.0.3 on
2026-09-09) under a new group `androidx.room3`. CLAUDE.md asks for the latest stable, this
database is new (no migration to pay), and starting on 2.8 would mean a package migration
later. What changes for us: KSP only (already the case), every DAO function is `suspend` or
returns `Flow`, a `SQLiteDriver` is mandatory (we use `AndroidSQLiteDriver`, the framework
SQLite, already in `room3-runtime-android` through `androidx.sqlite:sqlite-framework:2.7.1`,
no native library to ship), transactions are `withWriteTransaction { }` / `@Transaction`,
and `useReaderConnection` replaces raw cursors. **Fallback:** if Room 3 hits a blocker that
costs more than an hour (KSP or Hilt interplay, Robolectric and the driver), stop and tell
the manager; switching to `androidx.room:*:2.8.5` keeps the same entities and DAOs with
package renames only. Do not silently mix both.

**Driver:** `AndroidSQLiteDriver` (framework SQLite). `BundledSQLiteDriver` adds about 1 MB
per ABI and is only needed for FTS5; T08 (search) may revisit this, and switching drivers is
a one-line builder change.

### 3.3 Room schema (version 1)

`@Database(entities = [...], version = 1, exportSchema = true)` `abstract class GzaDatabase : RoomDatabase()`,
`@TypeConverters(Converters::class)`. Built in `DatabaseModule`:
```kotlin
Room.databaseBuilder<GzaDatabase>(context, "gza.db")
    .setDriver(AndroidSQLiteDriver())
    .setQueryCoroutineContext(ioDispatcher)
    // Everything in this database is re-fetchable from the gateway; user data lives in
    // DataStore. Remove this once Room holds anything that is not (observations, T19+).
    .fallbackToDestructiveMigration(dropAllTables = true)
    .build()
```
No foreign keys (reason: route data can arrive before the catalog on a first launch that is
briefly offline, stops-of-patterns may name stops the weekly catalog does not have yet, and
cascades plus `REPLACE` conflict strategy silently delete children). Integrity is kept by the
transactions in 3.5. **Never use `OnConflictStrategy.REPLACE`**: use `@Upsert` or explicit
delete then insert.

All ids are TEXT as the gateway sends them (`1:970`). Enum columns are TEXT by name
(`TransportKind`). Instants are INTEGER epoch millis (`Converters`). `DayOfWeek` is INTEGER
ISO 1..7.

| Table | Columns (PK in bold) | Indices | Rows (real data) |
|---|---|---|---|
| `stops` | **id**, code?, name_en?, name_ka?, lat, lon, kind | `code` | 2,753 |
| `routes` | **id**, short_name, long_name_en?, long_name_ka?, color? (INT 0xRRGGBB), kind | | 280 |
| `stop_routes` | **stop_id, route_id** | `route_id` | ~5 per synced stop |
| `patterns` | **route_id, suffix**, direction_id?, first_stop_id?, first_stop_name_en?, first_stop_name_ka?, last_stop_id?, last_stop_name_en?, last_stop_name_ka?, headsign_en?, headsign_ka? | | 2 per route |
| `pattern_stops` | **route_id, suffix, seq** (0-based travel order), stop_id | `stop_id` | ~50 per pattern |
| `polylines` | **route_id, suffix**, encoded, color? | | 2 per route |
| `schedule_periods` | **route_id, suffix, period_index**, from_day, to_day, service_dates (TEXT, sorted ISO dates joined by `,`, may be empty) | | 2 or 3 per pattern |
| `schedule_stop_times` | **route_id, suffix, period_index, seq** (row index in the response), position (gateway's value), stop_id, times (BLOB, 3.4) | `stop_id` | ~50 per period |
| `sync_state` | **key** (TEXT, 3.7), synced_at (INTEGER), last_used_at? (INTEGER) | | 2 + synced routes and stops |

Notes:
- `seq` is the list index, not the gateway's `position`: a loop route may list a stop twice
  (`PatternStops` KDoc) and a bad response could repeat a position; a PK on `position` would
  then abort the whole transaction.
- `defaultPatternSuffix` is **not stored** (TTC_API.md: it flips within an evening; "never
  cache it"). A `RouteDetail` read from Room has `defaultPattern = null`.
- `stop_routes` is not in the backlog's list but T07 needs "which routes serve my saved
  stop" offline (`/v2/stops/{id}/routes`); it is tiny and synced like route data.
- Stop names from schedule rows are not stored (`ScheduledStop.name` comes back `null`); the
  stop table has them in both languages.

Schema export: the Room 3 plugin writes `core/data/schemas/ge.hackerman.gza.core.data.database.GzaDatabase/1.json`,
**committed**. Migration approach for later versions: every version bump adds a `Migration`
(or `@AutoMigration`) and a `MigrationTestHelper` test; `GzaDatabaseSchemaTest` exists from
v1 so the harness is proven before it is needed (3.3 test list in 5.2).

### 3.4 Schedule storage: per-period rows with packed minutes (item e)

Measured on the real fixtures in `core/ttc/src/test/resources/fixtures/schedule/`:

| Pattern | Periods | Stop rows | Times | JSON chars of times |
|---|---|---|---|---|
| 301 0:01 | 3 | 177 | 10,915 | 63,704 |
| 301 1:01 | 3 | 180 | 11,100 | 64,789 |
| 326 0:01 | 2 | 92 | 4,232 | 24,846 |
| 326 1:01 | 2 | 90 | 4,410 | 25,750 |
| 472 0:03 | 2 | 86 | 3,311 | 19,158 |
| 472 1:03 | 2 | 96 | 3,696 | 21,388 |
| 551 0:01 | 3 | 156 | 11,596 | 67,428 |
| 551 1:01 | 3 | 156 | 11,596 | 67,623 |
| **Total (4 routes)** | 20 | **1,033** | **60,856** | 354,686 |

Rows past midnight (a time of 24:00 or later): 301 has 75 and 80 such stop rows, 326 has 4
and 3; 472 and 551 none.

Options for the 4 routes above:
- **Row per time** (`route, suffix, period, seq, minute`): 60,856 rows. At roughly 25 bytes
  per row plus about 30 bytes per index entry (on `stop_id` for the per-stop query) that is
  about 3.3 MB, and 60 k inserts per full refresh.
- **Text per stop row** (the gateway string `7:07,7:21,...`): 1,033 rows, about 355 KB of
  text, parsed on every read.
- **Chosen: packed BLOB per stop row**: 1,033 rows, times as big-endian unsigned 16-bit
  service minutes, 2 bytes each: 121,712 bytes of blobs, plus about 60 bytes of row and index
  overhead per row (about 62 KB): **about 185 KB for the four busiest routes the user has**,
  about 45 to 60 KB for one busy route. A user with 15 routes stays under 1 MB. One refresh of
  a route is about 300 inserts. Decoding the 67 departures of `1:970` for one period is a
  loop over 134 bytes.

Why this shape: every consumer reads a whole stop row (T05 needs "departures of route R at
stop S for the matching period", T10 needs whole pattern timetables), never a range of
minutes, so SQL never has to look inside the list. The only query is by `stop_id` (indexed)
or by `(route_id, suffix)` (PK prefix).

`PackedMinutes` (internal object, pure Kotlin, unit tested):
```kotlin
internal object PackedMinutes {
    fun pack(times: List<ServiceMinute>): ByteArray        // 2 bytes each, big-endian, order kept
    fun unpack(bytes: ByteArray): List<ServiceMinute>      // skips values >= 2880 and a trailing odd byte
}
```
`ServiceMinute` is 0..2879 (hours 0..47), which fits 16 bits. Order is kept exactly as the
gateway sent it (ascending today); T05 owns any sorting or selection. Values past midnight
(`24:05` = 1445) are stored as they are, **relative to the service day**, never converted to
an instant or a calendar date: that keeps "a 24:05 departure belongs to the service day it is
listed under" (TTC_API.md) and makes the database independent of the device time zone (3.7).

`service_dates` are stored exactly as received and **never filtered or pruned**, even when
they are all in the past: T05 matches by weekday once past the listed week, and the 12 h
refresh on app open normally brings the new week's dates.

### 3.5 Transactions: replacing data atomically (item d)

Rule: **fetch everything first, in memory; write in one transaction; write nothing on any
failure.** Readers (Room `Flow`s) only ever see committed states, and Room emits once per
transaction.

`RouteDataDao` is an `abstract class` so it can hold `@Transaction open suspend fun`s:
```kotlin
@Transaction
open suspend fun replaceRouteData(routeId: String, data: RouteDataRows, syncState: SyncStateEntity) {
    deletePatterns(routeId); deletePatternStops(routeId); deletePolylines(routeId)
    deleteSchedulePeriods(routeId); deleteScheduleStopTimes(routeId)
    insertPatterns(data.patterns); insertPatternStops(data.patternStops); insertPolylines(data.polylines)
    insertSchedulePeriods(data.periods); insertScheduleStopTimes(data.stopTimes)
    insertStopsIfAbsent(data.stopsFromPatterns)        // @Insert(onConflict = IGNORE): keeps bilingual names
    insertRouteIfAbsent(data.routeFromDetail)          // IGNORE: the catalog row wins
    upsertSyncState(syncState)
}
```
`RouteDataRows` is a plain holder of entity lists built by `EntityMappers` before the
transaction. Same pattern for:
- `StopDao.replaceAll(stops, syncState)`: `DELETE FROM stops`, insert all, upsert sync state.
  Delete-all plus insert is used instead of "delete where id not in (...)" because SQLite on
  API 26 limits bound variables to 999, and 2,753 ids would overflow it. Never bind an
  unbounded list anywhere in this module.
- `RouteDao.replaceAll(routes, syncState)`: same.
- `StopRoutesDao.replaceForStop(stopId, routeIds, routesIfAbsent, syncState)`.

Partial route failure (one pattern's schedule is a 500): the whole route refresh fails and
the previous data stays, status `Failed`. Acceptable: a route whose detail fails is useless
anyway, and a half-updated route (new stop order, old timetable) would be worse.

### 3.6 Guards and the error model (items b, h)

**Guards before any write** (defence in depth on top of T03's all-misfit `Malformed` rule):

| Sync | Rejected when | Result |
|---|---|---|
| Stops | the EN list is empty, or it has fewer than 50% of the rows currently cached | `Failed(EMPTY_OR_SHRUNK)`, nothing written |
| Routes | same rule | same |
| Route data | `RouteDetail.patterns` is empty while the cache has patterns for it | same |
| Route data, per pattern | the new pattern stops or schedule periods are empty while the cached ones are not | keep the cached rows for that component (copy them into `RouteDataRows`), write the rest, log once |
| Stop routes | the new list is empty while the cache has rows | keep the cache, `Failed(EMPTY_OR_SHRUNK)` |

The 50% floor: the network changes by a handful of stops a week; a truncated or filtered
response is far likelier than half the city disappearing. Constant `MIN_RETAINED_FRACTION = 0.5`
in `CatalogSync`, with a comment. A first sync (empty table) accepts any non-empty list.

Stop names: stops are fetched in EN and KA and merged by id. EN is the id list of record;
a stop missing from the KA list gets `name_ka = null`; a KA-only id is ignored. Same for
routes (`long_name_en/ka`) and route detail (`headsign_en/ka`, first/last stop names).
Both language calls must succeed or nothing is written. (Assumption to verify, see 6.3: the
EN and KA lists have the same ids.)

**Error model.** `TtcGatewayException` never leaves `:core:data`. `SyncErrors.kt`:
```kotlin
enum class SyncError { OFFLINE, NO_KEY, SERVER, MALFORMED, EMPTY_OR_SHRUNK, STORAGE }

internal fun Throwable.toSyncError(): SyncError = when (this) {
    is TtcGatewayException.Network -> SyncError.OFFLINE
    is TtcGatewayException.NoKey -> SyncError.NO_KEY
    is TtcGatewayException.Http -> if (code == 401 || code == 403) SyncError.NO_KEY else SyncError.SERVER
    is TtcGatewayException.Malformed -> SyncError.MALFORMED
    is androidx.sqlite.SQLiteException, is java.io.IOException -> SyncError.STORAGE
    else -> throw this      // programming errors surface in tests, never disguised
}

internal fun SyncError.isRetryable(): Boolean = this != SyncError.STORAGE  // worker backoff decides
```
(Check the exact exception class Room 3's driver throws for disk full or I/O errors:
`androidx.sqlite.SQLiteException` for the driver API; `android.database.SQLException` may
still escape from `AndroidSQLiteDriver`. Map both.) `CancellationException` is always
rethrown before this mapping. HTTP 401 after the interceptor's own refetch means the key is
dead: shown as `NO_KEY`, and the 12 h / weekly cadence retries later.

```kotlin
sealed interface SyncOutcome {
    data object Synced : SyncOutcome
    data object UpToDate : SyncOutcome                     // skipped, not stale
    data class Failed(val error: SyncError) : SyncOutcome
}

/** What a screen shows. Built from Room plus the in-memory sync status. */
sealed interface CachedResult<out T> {
    data object Loading : CachedResult<Nothing>                         // nothing cached, a sync is running or about to
    data class Data<out T>(
        val value: T,
        val syncedAt: Instant?,
        val freshness: Freshness,                                       // FRESH or STALE (3.7)
        val refreshError: SyncError?                                    // last attempt failed; data is still good to show
    ) : CachedResult<T>
    data class Unavailable(val error: SyncError) : CachedResult<Nothing> // nothing cached and the last attempt failed
}
enum class Freshness { FRESH, STALE }
```
These map to the backlog's "fresh, stale-cached, offline-no-data": `Data(FRESH)`,
`Data(STALE)` (or `Data(FRESH, refreshError != null)` briefly), `Unavailable(OFFLINE)`.
The types live in `:core:data` `model/`, not `:core:model` (fewer shared files with T05, and
only features that already depend on `:core:data` use them).

`SyncStatusTracker` (`@Singleton`, in memory): `StateFlow<Map<SyncKey, KeyStatus>>` with
`KeyStatus(inFlight: Boolean, lastError: SyncError?, lastAttemptAt: Instant?)`. Syncs call
`begin(key)` and `end(key, outcome)` in `try/finally`. Deriving a `CachedResult` for a key:

| Room has data | inFlight | lastError | Result |
|---|---|---|---|
| no | yes | any | `Loading` |
| no | no | null | `Loading` (no attempt yet; the trigger in 3.11 starts one) |
| no | no | set | `Unavailable(lastError)` |
| yes | any | any | `Data(value, syncedAt, freshness(syncedAt), lastError)` |

In-memory status is deliberate: after a process restart the first attempt is fresh anyway,
and persisting errors would show yesterday's "offline" today.

### 3.7 Time, staleness and keys (items f, g)

`sync_state.key` values, built only by `SyncKey`:
`SyncKey.Stops` = `"stops"`, `SyncKey.Routes` = `"routes"`, `SyncKey.Route(id)` = `"route:1:R97493"`,
`SyncKey.StopRoutes(id)` = `"stop-routes:1:970"`.

```kotlin
data class StalenessPolicy(
    val catalogMaxAge: Duration = Duration.ofDays(7),
    val routeMaxAge: Duration = Duration.ofHours(12),
    val stopRoutesMaxAge: Duration = Duration.ofDays(7),
    /** Routes used within this window are refreshed on app open; others wait for their next use. */
    val activeRouteWindow: Duration = Duration.ofDays(14),
    /** A synced_at further in the future than this means the device clock moved: treat as stale. */
    val futureTolerance: Duration = Duration.ofMinutes(5)
) {
    fun freshness(syncedAt: Instant?, maxAge: Duration, now: Instant): Freshness = when {
        syncedAt == null -> Freshness.STALE
        syncedAt > now + futureTolerance -> Freshness.STALE
        Duration.between(syncedAt, now) >= maxAge -> Freshness.STALE
        else -> Freshness.FRESH
    }
}
```
Every class takes the injected `java.time.Clock` (from `AppModule`, zone `Asia/Tbilisi`);
nothing calls `Instant.now()` or `System.currentTimeMillis()`. Staleness is pure duration
arithmetic on `Instant`s, so it does not depend on any zone. Freshness is computed when a
flow emits; it does not flip on its own while nothing changes. That is fine for T04 (the
next refresh trigger re-emits); T07 may combine with a minute ticker if it needs to show the
age live.

Tbilisi time: the database stores no local times at all. Service minutes are relative to
the service day, service dates are ISO `LocalDate`s as the gateway sent them (Tbilisi dates),
`synced_at` is UTC epoch millis. `TimeZoneIndependenceTest` proves nothing changes with the
JVM default zone set to `America/New_York` and `Pacific/Kiritimati`.

### 3.8 DataStore: preferences and the gateway config (items a, j)

Two typed DataStore files, both JSON through kotlinx.serialization (one small generic

### 3.9 Backup and data extraction (item c)

Decision: **back up only `files/datastore/user_prefs.json`**, on both paths (cloud backup and
device-to-device transfer). Everything else is excluded by being not included.

| Data | Backed up | Why |
|---|---|---|
| `user_prefs.json` (saved stops, walk times, route filters, buffer) | yes | User-authored, tedious to recreate, a few hundred bytes |
| `gza.db` (Room cache) | no | Re-fetchable in about 1 MB of downloads; restoring an old cache would only be stale |
| `ttc_config.json` | no | Carries the gateway key and a Firebase installation (fid, refresh token): device-specific, must not be cloned to another device, and the key may have rotated |
| WorkManager's database, shared prefs | no | Platform state, recreated on launch |

Saved stops hint at where the user lives and works, so cloud backup requires client-side
encryption: `disableIfNoEncryptionCapabilities="true"` on `<cloud-backup>` (Android 12+) and
`requireFlags="clientSideEncryption"` on the Android 11-and-lower include (honoured from
API 28; on 26 and 27 the flag is ignored and the file is backed up anyway, accepted).

`app/src/main/res/xml/data_extraction_rules.xml`:
```xml
<data-extraction-rules>
    <cloud-backup disableIfNoEncryptionCapabilities="true">
        <include domain="file" path="datastore/user_prefs.json" />
    </cloud-backup>
    <device-transfer>
        <include domain="file" path="datastore/user_prefs.json" />
    </device-transfer>
</data-extraction-rules>
```
`app/src/main/res/xml/backup_rules.xml`:
```xml
<full-backup-content>
    <include domain="file" path="datastore/user_prefs.json" requireFlags="clientSideEncryption" />
</full-backup-content>
```
Manifest: `android:allowBackup="true"` (needed for any backup on Android 11 and lower), and
the comment updated to say what is backed up and why. Comments in both XML files explain the
decision and point at `DataStoreFiles`.

### 3.10 Sync engines

All three are `@Singleton` classes with `@Inject` constructors taking `TtcGatewayClient`,
DAOs, `GzaDatabase` (for transactions if not in a DAO), `SyncStatusTracker`,
`StalenessPolicy`, `Clock`, `@IoDispatcher`. Each serializes per key with `KeyedMutex`
(a `ConcurrentHashMap<SyncKey, Mutex>`), re-checks staleness **inside** the lock (the second
of two parallel callers returns `UpToDate` without a request), wraps the gateway calls and
the write in `try { } catch`, maps errors (3.6) and updates the tracker in `finally`.

**`CatalogSync`**
```kotlin
suspend fun syncIfStale(maxAge: Duration = policy.catalogMaxAge): SyncOutcome   // stops and routes, each by its own key
```
Stops: `stops(EN)` and `stops(KA)` concurrently, merge, guard, `StopDao.replaceAll`. Routes:
`routes(EN)` and `routes(KA)`, same. Stops and routes are independent: routes are written
even if stops failed; the outcome is the worse of the two (`Failed` if either failed).

**`RouteSync`**
```kotlin
suspend fun syncIfStale(id: RouteId): SyncOutcome   // also sets last_used_at = now, even when UpToDate
suspend fun sync(id: RouteId): SyncOutcome          // forced
suspend fun refreshActiveRoutes(): Unit             // app open: stale routes used within activeRouteWindow
```
Order: `route(id, EN)` and `route(id, KA)` concurrently (the suffixes come from EN; KA only
adds names); then for each suffix `patternStops(id, suffix, EN)` and `schedule(id, suffix, EN)`,
plus one `polylines(id, allSuffixes)`, concurrently but through a module-wide
`Semaphore(4)` so three routes syncing at once still keep at most 4 requests in flight
(politeness, PLAN.md 3.2). A route with 2 patterns costs 7 requests, about 80 to 200 KB.
Language-neutral data (stop order, times, shapes) is fetched once in EN.

**`StopRoutesSync`**
```kotlin
suspend fun syncIfStale(stopId: StopId): SyncOutcome
```
`stopRoutes(stopId, EN)`; the routes it returns are inserted if absent (so the stop's route
list shows before the weekly catalog has run).

### 3.11 Scheduling: WorkManager and app open (item i)

**`CatalogSyncWorker`** (`@HiltWorker`, `CoroutineWorker`,
`@AssistedInject constructor(@Assisted context, @Assisted params, private val catalogSync: CatalogSync)`):
- Periodic run: `catalogSync.syncIfStale(maxAge = 6 days)` (a one-time run may have just
  refreshed; 6 days keeps the weekly cadence without doubling up).
- One-time run (input data `force = true` absent): `syncIfStale()` with the default 7 days,
  or any age when the tables are empty.
- `Synced`/`UpToDate` give `Result.success()`. `Failed` with a retryable error gives
  `Result.retry()` while `runAttemptCount < 5`, else `Result.success()` (wait for the next
  period instead of retrying forever). `STORAGE` gives `Result.failure()`.

**`SyncScheduler`** (`@Singleton`, wraps an injected `WorkManager`):
```kotlin
fun ensurePeriodicCatalogSync()     // enqueueUniquePeriodicWork("catalog-sync-weekly", KEEP, request)
fun requestCatalogSyncNow()         // enqueueUniqueWork("catalog-sync-now", KEEP, oneTimeRequest)
```
Periodic request: 7-day interval, constraints `NetworkType.CONNECTED` and
`setRequiresBatteryNotLow(true)`, `BackoffPolicy.EXPONENTIAL` from 15 minutes. `KEEP` so
calling it on every start never resets the schedule. A new periodic request's first run is
immediate once constraints hold, which covers the first launch. One-time request: only
`CONNECTED`, same backoff, no battery constraint (the user is waiting), **not expedited**
(expedited work needs a foreground notification below API 31). Both carry the tag
`catalog-sync`.

**`AppOpenSync`** (`@Singleton`, a `DefaultLifecycleObserver` registered on
`ProcessLifecycleOwner` in `GzaApplication.onCreate`). On every `onStart` it launches on
`@ApplicationScope`:
1. `scheduler.ensurePeriodicCatalogSync()`.
2. If the stops or routes table is empty or its `synced_at` is older than
   `catalogMaxAge + 1 day`: `scheduler.requestCatalogSyncNow()` (the periodic job is late or
   failing).
3. `routeSync.refreshActiveRoutes()`: routes with `last_used_at` within 14 days and
   `synced_at` older than 12 h, sequentially through `syncIfStale` (errors only go to the
   tracker). This runs in the app process, not WorkManager: it is "on app open" by
   definition, it is cheap when nothing is stale (one indexed query), and if the device is
   offline it simply fails and the next open retries.
4. `contentLanguage.refresh()` (3.12).
No throttle needed: every step is a no-op when nothing is stale, and `KEEP` makes repeated
enqueues free.

First use of a route or a stop's routes is triggered by the feature (T07/T08/T11 view
models call `routeRepository.refreshRouteIfStale(id)` / `stopRepository.refreshStopRoutesIfStale(id)`),
never as a hidden side effect of collecting a flow.

**Hilt and WorkManager wiring in `:app`.**
- `GzaApplication : Application(), Configuration.Provider` with
  `@Inject lateinit var workerFactory: HiltWorkerFactory` and
  `override val workManagerConfiguration get() = Configuration.Builder().setWorkerFactory(workerFactory).build()`;
  `@Inject lateinit var appOpenSync: AppOpenSync`;
  `onCreate` adds the observer to `ProcessLifecycleOwner.get().lifecycle`.
- `AndroidManifest.xml` removes the default initializer (on-demand initialization):
  ```xml

      android:authorities="${applicationId}.androidx-startup"
      android:exported="false"
      tools:node="merge">
      <meta-data
          android:name="androidx.work.WorkManagerInitializer"
          android:value="androidx.startup"
          tools:node="remove" />
  </provider>
  ```
  Keep `ProcessLifecycleInitializer` (do not remove the whole provider).
- `app/build.gradle.kts`: `implementation(projects.core.data)`, `implementation(libs.androidx.work.runtime.ktx)`,
  `implementation(libs.androidx.hilt.work)`, `implementation(libs.androidx.lifecycle.process)`.
- `app/src/test/resources/robolectric.properties` gains `application=android.app.Application`:
  the existing Robolectric app tests host composables in a plain `ComponentActivity`, and

### 3.12 Repositories and language

`ContentLanguage` (interface): `val language: StateFlow<Language>`, `fun refresh()`.
`AndroidContentLanguage` (`@Singleton`): on API 33+ reads
`context.getSystemService(LocaleManager::class.java).applicationLocales`, falling back to
`context.resources.configuration.locales`; first locale `ka` gives `Language.KA`, anything
else `Language.EN` (the app ships en and ka strings only; RU names are not synced). It also
registers `ComponentCallbacks` on the application context and refreshes in
`onConfigurationChanged`. The pure mapping `languageFor(locale: Locale): Language` is unit
tested; view models survive a language change, which is why the repositories combine with
this flow instead of reading the language once.

Name picking: `KA` uses `name_ka ?: name_en`, `EN` uses `name_en ?: name_ka`; a stop with
neither is dropped on read (it cannot be shown). Same for route long names and headsigns.

```kotlin
interface StopRepository {
    fun observeStops(): Flow<CachedResult<List<Stop>>>
    fun observeStop(id: StopId): Flow<Stop?>
    fun observeStopRoutes(id: StopId): Flow<CachedResult<List<Route>>>
    suspend fun refreshStopRoutesIfStale(id: StopId): SyncOutcome
}

interface RouteRepository {
    fun observeRoutes(): Flow<CachedResult<List<Route>>>
    fun observeRoute(id: RouteId): Flow<CachedResult<RouteBundle>>
    fun observeSchedule(id: RouteId, pattern: PatternSuffix): Flow<RouteSchedule?>
    /** Each schedule's periods hold only the rows for [stopId] (a loop route can have two). */
    fun observeSchedulesAtStop(stopId: StopId): Flow<List<RouteSchedule>>
    suspend fun refreshRouteIfStale(id: RouteId): SyncOutcome
    suspend fun refreshRoute(id: RouteId): SyncOutcome
}

/** A cached route: detail (defaultPattern always null), stop order and shapes per pattern. */
data class RouteBundle(
    val route: Route?,                                   // catalog row, null before the catalog sync
    val detail: RouteDetail,
    val patternStops: Map<PatternSuffix, PatternStops>,
    val polylines: Map<PatternSuffix, RoutePolyline>
)
```
Implementations `OfflineFirstStopRepository` and `OfflineFirstRouteRepository` build each flow
as `combine(daoFlow, syncStateDao.observe(key), tracker.status(key), contentLanguage.language) { ... }`
with the mapping on `@DefaultDispatcher` (`flowOn`), then `distinctUntilChanged()`. They
never touch the network except inside the `refresh*` functions, which delegate to the sync
engines. `PatternStops.stops` are joined with the `stops` table for names and coordinates;
a pattern stop whose id is missing from `stops` is kept using what was inserted from the
pattern response (3.5 inserts it if absent), so the join is never lossy.

DAO read queries return entity lists or `@Relation`-free projections; the joins
(`pattern_stops` with `stops`) are explicit SQL `LEFT JOIN`s returning a small data class.

`DataModule` binds `StopRepository`, `RouteRepository`, `UserPreferencesRepository`,
`TtcConfigCache` and `ContentLanguage` (`@Binds`, `@Singleton` on implementations), and
provides the default `StalenessPolicy()`.

### 3.13 Data flow summary

```
ProcessLifecycleOwner.onStart -> AppOpenSync -> SyncScheduler (WorkManager) -> CatalogSyncWorker -> CatalogSync
                                            \-> RouteSync.refreshActiveRoutes
Feature VM -> Repository.refresh*IfStale ---------> RouteSync / StopRoutesSync
Sync engines: TtcGatewayClient (in memory) -> guards -> one Room transaction -> sync_state
Repository.observe*: Room Flow + sync_state + SyncStatusTracker + ContentLanguage -> CachedResult<T>
```

## 6. Risks and open questions

### 6.1 Files shared with T05 (likely merge conflicts)

| File | T04 change | Mitigation |
|---|---|---|
| `gradle/libs.versions.toml` | add room3, datastore, lifecycle-process, robolectric plugin alias; delete room 2.8 entries | Keep additions in their own lines next to related entries; whoever merges second rebases and re-sorts. Never re-order unrelated lines. |
| `settings.gradle.kts` | one `include(":core:data")` | Trivial to merge. |
| `core/model/src/main/kotlin/.../` | **new files only**: `SavedStop.kt`, `UserSettings.kt` | If T05 introduces its own walk or buffer type (for example a `LeaveByInput`), reconcile after both merge: T05's engine should take `SavedStop.walkMinutes` and `UserSettings.bufferMinutes` as plain ints, not duplicate the preference model. The manager should tell T05's implementer these names. |
| `core/ttc/src/test/resources/fixtures/` | adds KA files only | Only run the `ka` recording mode. |
| `core/ttc/.../FirebaseRemoteConfigClient.kt` | best-effort installation calls | T05 does not touch `:core:ttc` main code. |
| `build-logic/` | new Robolectric plugin, screenshot plugin trimmed | T05 is pure JVM and should not touch it. |

T05 consumes `RouteSchedule`, `ServicePeriod`, `ScheduledStop`, `ServiceMinute` exactly as
T03 defined them; T04 does not change these types. If T05 changes them (for example makes
`ScheduledStop.name` non-null or adds fields), T04's mappers need a follow-up.

### 6.2 Technical risks

- **Room 3 is new** (stable since July 2026): fewer examples. Watch: the `room3 {}` DSL name,
  `@Transaction` on `open suspend fun` in an abstract DAO, `MigrationTestHelper` under
  Robolectric, KSP 2.3.12 plus Hilt 2.60.1 in the same module. Fallback in 3.1.
- **AGP 9 test source wiring** for the shared fixtures and schema assets (3.2): two options
  given; do not copy the fixtures.
- **Robolectric and the app's Hilt application**: setting `application=android.app.Application`
  for `:app` unit tests is required once `GzaApplication` starts syncing; any test that later
  needs Hilt must use `@HiltAndroidTest` with `HiltTestApplication` explicitly.
- **WorkManager on-demand init**: forgetting the manifest `tools:node="remove"` makes
  WorkManager initialize with the default factory and the `@HiltWorker` fails with
  "could not create worker". `SyncSchedulerTest` does not catch that; the manual step 2 and
  logcat do.
- **Transaction size**: replacing 2,753 stops is one transaction of a few hundred ms on an old
  phone; it runs on the IO dispatcher and readers keep the old data meanwhile (WAL). Fine.
- **Bound variable limit** (999 on API 26): no query may bind a list whose size is not fixed
  and small. Code review must check every `IN (:list)`.
- **DataStore single instance**: each file has exactly one `DataStore` singleton; two would
  throw "multiple DataStores active for the same file".
- **Freshness does not tick** (3.7): a screen left open for 13 h still says FRESH until the next
  emission. T07 decides if it needs a ticker.
- **Deleted stops still saved as favourites**: a stop removed by the weekly catalog stays in
  `user_prefs.json`; `observeStop` returns null and T07 must show it as "no longer served"
  rather than crash.
- **Storage growth**: route data is never evicted in T04 (about 50 KB per used route, worst
  case all 280 routes near 15 MB). Follow-up: evict routes unused for 30 days in the weekly
  worker.
- **Language coverage**: only EN and KA names are synced; if Russian UI strings are added
  later, add `name_ru` columns and a migration.
